# Claude Code 팀 운영 가이드 (최종본)

이 문서는 읽는 용도입니다. 프로젝트 폴더에는 `project/` 안의 내용만 복사합니다.

## 1. 구조
- **팀장 = 메인 세션**: 계획, 위임, 기록, 동기화. 직접 코딩하지 않습니다.
- **팀원 = 서브에이전트 8명**: 각자 별도 컨텍스트에서 일하고 요약 보고만 올립니다.
- **기억 = docs/ 파일**: 대화가 아니라 파일로 상태를 공유합니다. 평소에는 `docs/INDEX.md` 한 장만 보시면 됩니다.

```
project/
├─ CLAUDE.md                 팀장 규칙 (자동으로 읽힘)
├─ .gitignore                GitHub에 올리면 안 되는 파일 목록
├─ .env.example              환경 변수 예시 (실제 값은 .env, 업로드 안 됨)
├─ .private/TERMS.md         사내 명칭 -> 공용 용어 대응표 (업로드 안 됨)
├─ .claude/
│  ├─ agents/                팀원 8명
│  └─ commands/              /milestone /gate /report /sync /cleanup /migrate /secure-check
└─ docs/
   ├─ INDEX.md               한 장 요약 (사용자가 보는 화면)
   ├─ PLAN.md                목표·범위·아키텍처
   ├─ REQUIREMENTS.md        R: 요구 + 팀장의 이해
   ├─ DECISIONS.md           D: 유효한 결정
   ├─ PENDING.md             P: 논의 필요
   ├─ design/                architect 설계 문서 (작업 중 생성)
   ├─ history/LOG.md         시간순 활동 기록
   ├─ history/CHANGELOG.md   변경 이력 C
   └─ archive/               끝난 항목 보관 (작업 중 생성)
```

## 2. 적용 방법

### 새 프로젝트
`project/` 안의 내용 전체(숨김 폴더 `.claude` 포함)를 프로젝트 폴더에 복사한 뒤 Claude Code를 실행합니다.
`docs/PLAN.md`를 채우거나, 팀장에게 "PLAN.md 같이 채우자"라고 요청하시면 됩니다.

### 진행 중인 프로젝트 (기존 docs가 있는 경우)
터미널에서 압축을 푼 `claude-team-kit` 폴더로 이동한 뒤 실행합니다. `내프로젝트`는 실제 경로로 바꿔 주세요.
```bash
cp 내프로젝트/CLAUDE.md 내프로젝트/CLAUDE.md.bak 2>/dev/null   # 기존 규칙 백업
cp project/CLAUDE.md 내프로젝트/
cp -R project/.claude project/.private 내프로젝트/
cp -n project/.env.example 내프로젝트/
cp -Rn project/docs 내프로젝트/     # -n: 기존 문서는 덮어쓰지 않음
# .gitignore: 없으면 복사, 있으면 아래처럼 뒤에 이어 붙이기
[ -f 내프로젝트/.gitignore ] && cat project/.gitignore >> 내프로젝트/.gitignore || cp project/.gitignore 내프로젝트/
```
그다음 Claude Code를 새로 실행하고 `/migrate`를 실행합니다. 기존 문서는 `docs/archive/legacy/`에 보존되고, 기존 P-/D- 번호는 그대로 유지됩니다. 매핑표와 "분류 불가" 목록을 확인하신 뒤 승인하시면 됩니다.

> 탐색기나 Finder로 복사하실 때는 숨김 파일 표시를 켜야 `.claude` 폴더가 보입니다. 파일을 넣거나 바꾼 뒤에는 Claude Code를 재시작해야 반영됩니다.

## 3. 작업 흐름
1. `/milestone 로그인 기능 설계까지` → 팀장이 작업을 나눠 계획을 보여줌 → 승인
2. 팀장이 위임하고, 진행 상황을 한 줄씩 표시
   `→ architect | M1-2 로그인 설계 시작` / `← architect | M1-2 완료, P-04 등록`
3. 중간 확인은 `/report`, 요구사항이 바뀌면 `/sync 변경 내용`
4. 끝나면 `/gate` → 보고, 정리, 다음 범위 2안 제안 후 **멈춤** → 승인해야 다음으로

진행 속도는 마일스톤 범위로 조절합니다. 빨리 가고 싶으시면 범위를 크게, 꼼꼼히 보고 싶으시면 작게 정하시면 됩니다.

## 4. 명령어
| 명령 | 언제 | 하는 일 |
|---|---|---|
| `/milestone 범위` | 시작할 때 | 작업 분해, 담당 지정, 계획 승인 대기 |
| `/report` | 수시로 | INDEX만 읽고 10줄 보고 (토큰 적게 씀) |
| `/sync 변경 내용` | 요구가 바뀔 때 | 기록, 영향 분석, 승인 후 변경분만 전달 |
| `/gate` | 마일스톤 끝 | 보고, 정리, LOG 분리, 다음 범위 제안, 멈춤 |
| `/cleanup` | 문서가 지저분할 때 | 끝난 항목 보관, 요약, ID 일치 검사 |
| `/migrate` | 최초 1회 | 기존 문서를 새 구조로 이관 |
| `/secure-check` | 커밋·푸시 전 | 비밀값, 사내 명칭, 올리면 안 되는 파일 점검 (수정은 승인 후) |

## 5. 무엇을 어디서 찾나
| 찾는 것 | 파일 |
|---|---|
| 지금 상태, 모든 항목 요약 | docs/INDEX.md |
| 내 요구와 팀장의 이해 | docs/REQUIREMENTS.md |
| 확정된 결정 | docs/DECISIONS.md |
| 논의가 필요한 것 | docs/PENDING.md |
| 누가 언제 무엇을 했나 (판단과 이유 포함) | docs/history/LOG.md |
| 무엇이 어떻게 바뀌었나 | docs/history/CHANGELOG.md |
| 지난 마일스톤 기록 | docs/history/LOG-M1.md 등, docs/archive/ |

ID: **R** 요구 / **D** 결정 / **P** 논의 필요 / **C** 변경 / **M1-2** 마일스톤 작업

## 6. 팀원 (서브에이전트)
| 역할 | 하는 일 | 못 하는 것 | 모델 |
|---|---|---|---|
| analyst | 요구 분석, 기술 조사 | 코드 수정, 결정 | sonnet |
| architect | 구조·데이터·API 설계 | 구현 코드 작성 | opus |
| developer | 구현 | 삭제, 의존성 교체, 설계 변경 | sonnet |
| tester | 테스트 작성·실행 (tests/만) | 기능 코드 수정 | sonnet |
| reviewer | 코드 리뷰 | 모든 수정 (읽기 전용) | sonnet |
| debugger | 원인 분석, 최소 수정 | 증상 가리기, 설계 변경 | opus |
| documenter | README, 사용법 문서 | 팀장 문서 수정 | haiku |
| devops | 환경, 빌드, CI 설정 | 실제 배포, 비밀값 처리 | sonnet |

모든 팀원은 같은 형식으로 보고하고, 보고 끝에 "기록 항목"을 붙입니다. 팀장이 이것을 LOG에 옮깁니다.
에이전트를 바꾸고 싶으시면 `.claude/agents/`의 파일을 직접 고치거나, "debugger 모델을 sonnet으로 바꿔줘"처럼 요청하시면 됩니다.

## 7. 비용 절약 수칙
- 현황은 `/report`로 확인합니다. INDEX 한 장만 읽어서 가장 적게 씁니다.
- LOG와 CHANGELOG는 평소에 읽지 않도록 되어 있습니다. 쌓여도 비용이 늘지 않습니다.
- 팀장 세션이 길어지면 `/gate`나 `/report` 뒤에 `/clear`를 하세요. 규칙과 상태는 파일에 남아 있습니다.
- 메인 세션은 평소 Sonnet으로 쓰고, 큰 설계 판단이 필요할 때만 `/model`로 Opus로 바꾸시면 됩니다.
- 비용을 더 줄이려면 debugger를 sonnet으로 바꾸세요.

## 8. 알아둘 점
- 팀원의 작업은 화면에 접힌 요약으로만 보입니다. 위임과 완료를 한 줄씩 표시하게 해 두었지만, 팀원이 일하는 과정이 실시간으로 보이지는 않습니다.
- 서브에이전트는 다른 서브에이전트를 부를 수 없습니다. 모든 위임은 팀장이 합니다.
- 팀장은 계획에 없던 작업, 재작업, 되돌리기 어려운 작업을 하기 전에 반드시 확인을 받습니다.

## 9. 여러 프로젝트에서 공용으로 쓰기
- 키트 파일에는 특정 회사·특정 프로젝트 용어가 없습니다. 예시 행(로그인, Node.js 등)은 일반 예시이고, 실제 항목이 생기면 지워집니다.
- 프로젝트마다 `project/` 내용을 새로 복사해서 시작합니다. docs/는 프로젝트별 기록이므로 프로젝트끼리 섞지 않습니다.
- 프로젝트마다 달라지는 것은 docs/PLAN.md와 .private/TERMS.md 두 개뿐입니다. 나머지는 손대지 않고 그대로 씁니다.
- 키트 자체를 고치고 싶으시면 원본 키트를 고친 뒤 새 프로젝트에 복사하세요. 이미 진행 중인 프로젝트에는 바꾼 파일만 덮어쓰면 됩니다.
- 팀원 8명을 모든 프로젝트에서 따로 복사하지 않고 쓰고 싶으시면 `.claude/agents/`를 `~/.claude/agents/`에 두셔도 됩니다. 다만 CLAUDE.md, 명령어, docs는 프로젝트 폴더에 있어야 합니다.

## 10. GitHub 업로드 시 보안
모든 프로젝트가 GitHub 저장소에 올라간다는 전제로 규칙을 넣어 두었습니다.

**올리면 안 되는 것 (.gitignore로 막혀 있음)**
| 종류 | 예 |
|---|---|
| 비밀값 | .env, API 키, 토큰, 비밀번호, 인증서(.pem .key .p12), SSH 키 |
| 시리얼·라이선스 | 라이선스 파일(.lic), 시리얼·제품 키 |
| 사내 자료 | 사내 데이터, DB 덤프(.dump .bak), 내부 문서 원본 (data/private/, internal/에 둠) |
| 로컬 설정 | .claude/settings.local.json, CLAUDE.local.md, IDE 설정 |
| 로그·빌드 | *.log, node_modules/, dist/ 등 |

**.gitignore로 막을 수 없어 규칙으로 막는 것**
- 코드, 주석, docs, LOG, 커밋 메시지 안의 회사명·고객사명·사내 시스템명 → 공용 용어로 씁니다 (예: 사내 시스템명 → 미들웨어).
- 코드에 직접 적힌 서버 주소, IP, 계정 → 환경 변수로 뺍니다.
- 실제 고객·직원 데이터로 만든 테스트 데이터 → 가짜 데이터를 씁니다.

**공용 용어 대응표 (.private/TERMS.md)**
프로젝트를 시작할 때 사내 명칭과 바꿔 쓸 공용 용어를 적어 두세요. Claude는 이 표를 보고 저장소에는 공용 용어만 씁니다. 표에 없는 명칭이 나오면 공용 용어를 제안하고 추가할지 묻습니다. 이 파일은 업로드되지 않습니다.

**조심하실 점**
- `.gitignore`는 아직 추적되지 않은 파일만 막습니다. 이미 커밋된 파일은 `git rm --cached 파일명`으로 추적을 끊어야 합니다.
- 비밀값이 한 번이라도 커밋되어 푸시됐다면, 파일을 지워도 기록에 남습니다. **해당 키나 비밀번호를 즉시 폐기하고 새로 발급**하시는 것이 가장 확실합니다.
- 커밋·푸시는 승인 후에만 하도록 했고, 그 전에 `/secure-check`를 거치게 했습니다. 직접 커밋하실 때도 한 번 실행해 주세요.
- 저장소를 처음 만들 때는 Private으로 만들고, 점검이 끝난 뒤 공개 여부를 정하시는 것을 권해 드립니다. GitHub 저장소 설정의 Secret scanning과 Push protection을 켜 두시면 비밀값 푸시를 한 번 더 막아 줍니다.
- 회사 보안 정책상 사내 코드나 업무 내용을 개인 저장소에 올릴 수 있는지는 회사 규정을 먼저 확인하시는 것이 안전합니다.
