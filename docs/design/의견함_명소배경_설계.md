# 1부. 의견 보내기 (R-16)

## 1. 한눈에
- 오른쪽 위 도구 줄(`#tools`, 시계·자유게시판·이웃 등록 옆)에 **의견 보내기** 알약 버튼을 둡니다. 모바일은 아이콘만(쪽지 모양) 보입니다.
- 누르면 고양이 앞발 모양 팝업이 열립니다. 칸은 **제목 / 보내는 이(선택) / 내용(500자)** 세 개뿐입니다.
- 파일 첨부는 만들지 않습니다. 글자만 받습니다. 링크는 막거나 걸러 냅니다.
- 비회원도 보낼 수 있습니다(GATE 설정표에 `feedback: '누구나'` 한 줄 추가).

## 2. 서버 없이 0원으로 메일 받기 (비교)

| 방법 | 무료 한도 | 스팸 위험 | 장점 | 단점 |
|---|---|---|---|---|
| A. mailto 링크 | 무제한 | 낮음(내 메일 앱이 열릴 뿐) | 가장 간단 | **저장소에 이메일이 그대로 공개됨.** 메일 앱이 없는 사람은 못 보냄. 팝업이 의미 없어짐 |
| B. Formspree | 월 50건, 첨부 불가 [확인: formspree.io/plans] | 기본 스팸 필터 | 설정 쉬움 | 월 50건이 적음. 폼 주소가 공개됨 |
| C. EmailJS | 월 200건, 템플릿 2개 [확인: emailjs.com/pricing] | 공개 키가 코드에 노출되어 남이 대신 보낼 수 있음 [추측: 도메인 제한 설정 필요] | 서버 불필요 | 메일 서비스 계정을 연결해야 함 |
| D. Web3Forms | 월 250건, 보관 30일, 첨부는 유료 [확인: 검색 요약, web3forms.com/pricing은 직접 열리지 않음] | 고급 스팸 보호, 무료는 hCaptcha | 받는 메일은 그쪽 서비스에 등록되고 코드에는 "접근 키"만 들어감. 키는 공개되어도 되도록 설계됨 [추측: 이메일은 키에서 역추적되지 않음] | 외부 서비스 정책 변동 가능. 무료에서 Turnstile 불가 |
| E. Cloudflare Pages Function(Worker) | Workers 무료 등급 하루 약 10만 요청 [미확인: 공식 문서에서 다시 확인] | 서버 쪽에서 길이·쿨다운·Turnstile 검증 가능 | D-08과 같은 Cloudflare. 비밀값을 서버 환경 변수에 숨길 수 있음 | 메일을 실제로 보내려면 또 다른 메일 발송 서비스가 필요. 코드가 늘고 Pages Functions 사용으로 "빌드 없음" 느낌이 약해짐 |
| F. Supabase 저장 + 알림 | DB 무료. 알림 메일은 [미확인] 별도 서비스 필요 | RLS로 길이 제한, 삽입만 허용 | 의견이 **내 DB에 남음**, 어드민 목록으로 읽기 가능(D-12와 일치) | 메일이 "자동으로" 오지는 않음. 내가 열어 봐야 함 |

### 권장 (P-16)
- **1순위 D(Web3Forms)**: 코드에 비밀이 없고, 메일이 바로 오고, 월 250건이면 시연에 충분합니다.
- **보강 F(Supabase에도 저장)**: 메일이 막히거나 한도를 넘어도 의견이 남고, 어드민에서 모아 볼 수 있습니다. 배포(M4) 때 같이 붙이면 됩니다.
- A는 이메일이 공개되므로 제외, C는 키 남용 위험이 커서 보류, E는 나중에 스팸이 심해질 때 단계적으로 추가합니다.
- 어느 쪽이든 화면과 어댑터는 `Caps.feedback.send({title, from, body})` 한 함수 뒤에 숨겨서 나중에 바꾸기 쉽게 합니다(D-10과 같은 방식).

## 3. 공개 저장소에 이메일 숨기기 (P-07 연결)
- 이메일 주소는 **어떤 파일에도 쓰지 않습니다.** 받는 주소는 Web3Forms 대시보드(사용자 명의 계정, D-14)에만 등록합니다.
- 코드에는 "접근 키"만 들어갑니다. 이 키는 공개용(anon 키와 같은 성격)이라 괜찮습니다. 다만 P-07(빌드 없는 정적 사이트의 키 주입)이 정해져야 같은 방식으로 넣습니다. 임시로는 `src/config.js`에 공개 키 자리만 두고 값은 비워 둡니다.
- `.env.example`에는 설명만 추가합니다: `FEEDBACK_ACCESS_KEY=your-form-access-key (공개용, 받는 메일은 서비스 대시보드에 등록)`. 실제 값은 `.env`.
- 커밋 전 `/secure-check`에서 `@` 문자열(메일 형태)이 새로 들어갔는지 확인 항목으로 추가합니다.

## 4. 스팸·악용 방지와 개인정보

| 장치 | 방법 | 구현 위치 |
|---|---|---|
| 길이 제한 | 제목 40자, 보내는 이 40자, 내용 500자. 칸에 `maxlength` + 코드에서 한 번 더 자름 | 화면 |
| 용량 제한 | 전체 글자 합이 약 1.5KB(한글 3바이트 기준 600자)를 넘으면 거부. 파일·이미지 입력 칸 없음 | 화면·어댑터 |
| 허니팟 | 눈에 안 보이는 빈 칸을 하나 두고, 채워져 있으면 봇으로 보고 **성공한 척** 버림 | 화면 |
| 쿨다운 | 브라우저당 60초에 1회, 하루 5회(localStorage). 전송 실패는 횟수에 넣지 않음 | 화면 |
| 입력 시간 | 팝업을 연 뒤 3초 안에 전송되면 봇으로 판단 | 화면 |

## 5. 팝업 UX

| 상태 | 화면 문구 예시 |
|---|---|
| 처음 | 제목줄: "냥~ 의견을 들려주세요" / 부제: "혼자 만들고 있어서 부족한 점이 많아요. 고양이가 꼼꼼히 읽을게요." |
| 칸 이름 | 제목: "한 줄 제목" / 보내는 이: "이름이나 별명 (안 적어도 돼요)" / 내용: "불편했던 점, 바라는 점을 적어 주세요" 와 `0/500` 카운터 |
| 보내기 버튼 | "냥 하고 보내기" (비어 있으면 회색) |
| 전송 중 | 버튼이 "꾹꾹이 중…", 발바닥 아이콘이 통통 튐. 중복 클릭 막음 |
| 성공 | 고양이가 눈 감고 그르릉: "잘 도착했어요! 고마워요 🐾" 2초 뒤 자동으로 닫힘 |
| 실패 | 고양이가 갸우뚱: "앗, 가는 길에 길을 잃었어요. 잠시 뒤 다시 눌러 주세요." 입력한 글은 그대로 남김 |
| 쿨다운 | "방금 보내 주셨어요. 1분 뒤에 또 만나요" |
| 링크·필터 | "링크는 보낼 수 없어요. 글로만 적어 주세요" |

- 모양: 기존 `.panel`(예: `#card`) 스타일을 재사용. 위쪽에 고양이 귀 두 개, 모서리 둥글게, 아래에 발바닥 장식.
- 모바일: 화면 아래에서 올라오는 시트, 키보드가 올라와도 버튼이 가려지지 않게 `visualViewport` 높이를 따릅니다. 첫 칸 자동 포커스는 하지 않습니다(키보드가 장면을 가리므로).
- 접근성: 닫기 버튼과 Esc, 칸마다 라벨, 오류는 `aria-live`로 읽힘.

## 6. 로컬 시험 (모의 어댑터, D-21)
- 모의 `Caps.feedback.send`는 메일을 보내지 않고 localStorage의 `gn_feedback` 목록에 쌓습니다(이메일·키 불필요). 어드민 "의견함" 구역에서 읽습니다.
- 시험용 스위치: 성공 / 실패 / 느린 응답(3초) / 한도 초과를 어드민에서 고릅니다.
- 쿨다운·허니팟·길이·링크 차단은 화면 쪽 코드라 로컬에서 그대로 시험됩니다.
- 실제 Web3Forms 연결은 배포 후 1회 실전 확인(M4). 그 전까지는 모의 어댑터로만 통과 기준을 잡습니다.

## 7. 어드민 시험 구역 항목 (R-15 9장에 "의견함" 구역 추가)

# 2부. 지역 명소 배경 (R-17)

## 9. 고민 정리
1. 시/도 16곳은 명소를 정하기 쉽다. 시군구 256은 힘들어도 가능하다. **동 3,558은 명소를 특정하기 어렵다.**
2. 모든 곳을 Claude가 검색해서 채울 수 없다. 또 Claude의 기억은 작은 동네에서 틀릴 수 있다 [추측: 사실 오류 위험, 사용자 확인 필요].
3. 그래서 **"안 채워도 어색하지 않은 구조"**와 **"사용자가 원하는 만큼만 개입하는 구조"**가 핵심입니다.

## 10. 계층 상속·폴백 구조

조회 순서 (현재 `REGION_LEVEL` 기준 활성 지역 코드로 시작):

```
동(10자리) -> 시군구(5자리) -> 시/도(2자리) -> 지형·유형 자동 -> 기본 테마(골목·시장·공원)
```

| 단계 | 데이터가 있으면 | 없으면 |
|---|---|---|
| 동 | 그 동의 명소 | 시군구로 올라감 |
| 시군구 | 그 시군구의 명소 | 시/도로 올라감 |
| 시/도 | 그 시/도의 명소 | 자동 단계로 |
| 자동 | 이름 규칙·위치로 고른 지형 배경(바다, 산, 강, 논밭, 도심 등) | 기본 테마 |

- **상속 규칙**: 하위가 비어 있으면 상위 명소를 쓰되, 화면에는 "근처 명소" 표시로 구분합니다(정직한 표시). 상위 명소가 여러 개면 지역 코드로 결정적으로 하나 고릅니다(같은 동은 항상 같은 결과).
- **자동 지형** [추측: 정확도는 80% 정도 기대]: 지금 `themeFor()`처럼 이름 규칙을 씁니다(`면`→논밭·산, `천·강`→강변, `항·포·해`→바다, `시장`→시장 아케이드, `공원·숲`→숲). 시/도마다 지형 태그(해안/내륙/산지/섬)는 16곳이라 사람이 한 번에 정할 수 있습니다.
- **데이터 파일 하나로 관리**: `data/landmarks.json`(편집용 원본, 사람이 읽을 수 있는 형태). 배포용으로는 시/도 코드 2자리별 조각 `data/landmarks/11.json` 식으로 나눕니다(지연 로딩, 14장).
- 진행률을 눈으로 보기 위해 어드민에 "채워진 곳 / 상속 중인 곳" 지도를 둡니다(18장).

| 0 개입 | 없음 | 0 | 상속 + 자동 지형 |
| 1 최소 | 명소 **이름**만 말해 주기("시흥 - 오이도, 갯골생태공원") | 약 10초 | 이름으로 유형을 추정해 데이터에 추가, 추정한 유형을 목록으로 되돌려 확인 요청 |
| 2 중간 | 이름 + **유형 선택지**(바다/산/한옥/탑/다리/공원/시장/도심/섬/기타) + 한 줄 설명 | 약 30초 | 유형에 맞는 실루엣 부품 선택, 한 줄을 안내 문구로 사용 |
| 3 최대 | 직접 찍은 **사진** 제공 | 약 2~3분(촬영 제외, 권리 확인 포함) | 윤곽·색 팔레트만 추출해 실루엣에 반영(12장) |

### 현실적인 작업량 (3,000곳 가정, 사용자 시간)

| 전략 | 직접 다루는 곳 | 시간 [추측] | 나머지 |
|---|---|---|---|
| 시/도만 (1단계) | 16곳 × 평균 3개 = 약 48개 | 이름만이면 약 10분, 중간 단계면 약 25분 | 아래 모두 상속 |
| + 주요 시군구 (2단계) | 약 50곳 × 2개 = 약 100개 | 이름만 약 20분, 중간 약 50분 | 나머지 시군구는 상속 |
| + 전 시군구 (3단계) | 256곳 × 1~2개 = 약 400개 | 이름만 약 1시간 10분, 중간 약 3시간 | 동은 상속 |
| 동까지 전부 | 3,558곳 | 이름만 약 10시간, 중간 약 30시간, 사진 약 100~180시간 | 없음 |

- 전략: **상위 약 15%(시/도 + 주요 시군구 약 100~150개)만 직접, 나머지 85%는 자동·상속.** 동 단위는 "특징이 뚜렷한 곳 약 100~200개"(예: 해운대, 명동, 여의도처럼 이미 유명한 동)만 사용자가 지정하고 그 외는 비웁니다.
- 우선순위: ① 접속이 실제로 많은 지역(분석 데이터 D-12) ② 유명도 ③ 사용자가 아는 지역. 접속 통계가 생기면 "자주 보는데 상속 중인 곳"을 어드민이 알려 줍니다.
- Claude 검색에 맡기는 범위: 시/도, 주요 시군구의 **후보 목록 작성**(사용자가 고르기만 하면 되게). 작은 동네는 Claude가 후보를 만들지 않습니다(틀릴 위험).

## 12. 이름으로 전달 vs 사진으로 전달

| 항목 | 이름 | 사진 |
|---|---|---|
| 정확도 | 낮음~중간(유형·크기는 추정). 같은 이름이라도 모양은 일반화됨 | 높음(윤곽·색 실제 반영) |
| 사용자 수고 | 매우 적음 | 큼(촬영·고르기·전송·권리 확인) |
| 저작권 | 문제 없음(이름은 저작물이 아님) | **공개 저장소·공개 서비스에 올라가므로 위험.** 아래 참고 |
| 파일 크기 | 거의 0(글자 한 줄) | 사진 1장 100~300KB 이상(WebP 변환 후에도) [추측] |
| 로딩 | 코드로 그림 → 거의 0 | 이미지 로딩 필요, 3D 장면과 별도 다운로드 |
| 앱 구조 적합성 | 좋음(단일 index.html, 파일 최소) | 보통(파일 수 증가, 저장소 용량) |

### 저작권 정리 (법률 자문 아님 [추측], 확인 필요)
- 인터넷 사진을 복사해 쓰는 것은 **하지 않습니다.** 공개 GitHub 저장소는 누구나 내려받을 수 있어 재배포에 해당할 수 있습니다.
- **직접 찍은 사진**: 사용자가 저작권자이므로 가능. 사람 얼굴·번호판이 나오면 제외.
- **공공누리 제1유형** 공공저작물: 출처 표시만 하면 상업 이용·변형 모두 가능 [확인: 문화체육관광부 공공누리 안내, mcst.go.kr, 지자체 안내 페이지 다수]. 제2유형은 상업 이용 금지, 제3유형은 변형 금지, 제4유형은 둘 다 금지이므로 이 앱에서는 제1유형만 후보. 출처 표시를 화면 구석이나 `CREDITS`에 넣어야 합니다.
- 건축물·조형물 자체의 저작권(최근 건축물, 설치 미술)은 사진과 별개로 걸릴 수 있습니다 [추측/미확인]. 그래서 **실제 모양을 그대로 베끼지 않고 단순화한 실루엣**으로 가는 쪽이 안전합니다.
- 안 되는 것: 지도·포털·SNS·블로그 사진, 여행사 홍보 이미지, AI 이미지 생성기에 유명 건축물을 그대로 만들게 하는 것(결과물 권리 불명확).
- 사진이 기본 경로가 아니도록: 사진을 받으면 **원본은 저장소에 넣지 않고** 윤곽선(벡터 몇 십 점)과 팔레트(색 5개)만 뽑아 데이터에 넣습니다. 원본은 사용자 PC에만 둡니다(`.gitignore`의 사진 폴더).

## 13. 배경을 어떻게 만드나 (현실적 비교)

현재 장면 [확인: 코드]: 바닥 24m × 16m, 뒤쪽 담/생울타리가 z=-2, 안개(Fog) 9~28m, 해는 시각에 따라 움직임(`setTime`). 배경이 "원경"으로 담 뒤에 서 있을 자리가 있습니다.

| 방식 | 설명 | 용량 | 장점 | 단점 | 판정 |
|---|---|---|---|---|---|
| A. 절차적 3D 실루엣 부품 조합 | 부품 약 12~16종(산, 탑, 한옥 지붕, 성곽, 다리, 고층 빌딩군, 등대, 섬, 항구 크레인, 폭포, 논밭…)을 색·높이·개수 변수로 조합 | 코드 몇 KB, 명소 데이터는 한 줄 | 해·안개·밤과 자연스럽게 어울림, 용량 0, 무한 변주 | 부품 코드를 Claude가 한 번 짜야 함. 실제와는 "느낌"만 같음 | **권장(주)** |
| B. 2D 캔버스 층 그림(원경 카드) | 캔버스로 하늘 그라데이션 + 3겹 실루엣을 그려 평면 카드로 세움(시차 효과) | 코드 몇 KB | 가장 가볍고 빠름, 3D 부담 없음 | 입체감이 약함 | **권장(보조, 낮은 사양 대체)** |
| C. 스카이박스 이미지 | 사진·일러스트로 구 전체 배경 | 지역당 수백 KB~수 MB | 사실적 | 파일 큼, 권리 문제, 해·밤 바뀜에 안 맞음 | 비권장 |
| D. 사진 → 스타일화 | 사진을 윤곽·색으로 변환 | 원본 비포함 시 작음 | 정확도 높음 | 변환 도구 필요, 권리 확인, 품질 편차 | 사용자가 사진을 줄 때만 부분 사용 |
| E. 이미지 생성 AI | 명소 그림을 생성 | 큼 | 다양 | 무료 한도·상업 이용 조건 불명, 일관성 낮음 | 0원 원칙 충돌 가능, 제외 [미확인] |

- 권장: **A+B 하이브리드**. 장면 안에서 담 뒤(z=-9 ~ -14 부근, [미확인: 카메라 시야에서 보이는지 만들 때 확인])에 실루엣 군을 세우고, 안개 색을 입혀 멀리 보이게 합니다.
- 시/도 16곳에는 대표 명소 1~2개에만 **전용 모델**(예: 서울 N타워형 탑, 부산 광안대교형 다리)을 따로 짜고, 나머지는 부품 조합입니다.
- 부품은 `kind`(유형)로 연결: `tower, palace, hanok, fortress, bridge, harbor, lighthouse, mountain, island, falls, field, market, skyline, temple, park`.

## 14. 비용 논의 (약 3,000곳, 일주일마다 교체한다고 가정)

### 계산식과 가정
- 가정: 활성 지역 3,000곳 규모로 확장된 후, **매주 모든 곳의 배경을 새로 바꾼다**.
- 새 배경을 "새 그림/새 모델"로 만들면 연 3,000 × 52 = **156,000개**. 매주 3,000개.

### (1) 돈
| 방식 | 비용 |
|---|---|
| 절차적(A·B) | 0원. 저장은 글자 데이터, 전송도 Cloudflare Pages 정적 파일 |
| 이미지 생성/외주/유료 저장소 | **D-01(0원)과 충돌.** 무료 등급 한도·조건은 [미확인], 주 3,000장은 무료로 불가능할 가능성이 큼 [추측] |
| 저장 한도 [미확인] | Cloudflare Pages 무료의 파일 수·크기 한도, GitHub 저장소 권장 용량(약 1GB)은 구현 전 확인 |

### (2) 사용자 시간
- "주마다 사용자가 이름을 새로 준다"면 3,000곳 × 10초 = **주 8.3시간**. 사실상 불가능.
- 현실적: 1회 입력(11장) 후 주간 변화는 자동. 사용자는 분기에 한 번 몇 개 교체 정도.

### (3) Claude 작업량 (범위 추정 [추측], 실제와 다를 수 있음)
| 작업 | 가정 | 대략 |
|---|---|---|
| 부품 12~16종 코드 최초 작성 | 부품당 40~80줄 ≈ 0.7~1.5k 토큰 출력 | **2만~4만 토큰**, 1~2회 작업 |
| 시/도 전용 모델 16~24개 | 개당 100~200줄 ≈ 2~4k 토큰 | **4만~10만 토큰** |
| 명소 데이터 입력 | 1건 JSON ≈ 120~200 토큰 | 100건 ≈ 2만 / 500건 ≈ 10만 / 3,000건 ≈ 40만~60만 토큰 (+ 사용자 확인 대화) |
| 매주 3,000곳을 "새 3D 모델"로 교체 | 개당 3~5k 토큰 | **주 900만~1,500만 토큰, 비현실적** |
| 매주 3,000곳을 "데이터만" 교체 | 개당 150 토큰 | 주 약 45만 토큰 + 검증. 가능하지만 검증 부담이 큼 |
- 모르는 점: Claude가 작은 동네 명소를 정확히 아는지(낮을 수 있음), 한 세션에서 한 번에 처리 가능한 양. 소량(50~100건)씩 나누어 진행을 권장합니다.

### (4) 용량·로딩: 지역 하나만 지연 로딩
- 전체 데이터 3,000건 × 약 200바이트 ≈ **600KB** [추측]. 한 번에 올리지 않고, **시/도 조각**(약 190건 ≈ 40KB, 압축 시 더 작음)을 그 지역에 들어갈 때만 `fetch`합니다.
- 부품 코드는 한 번만 로드(약 20~40KB), 데이터에 따라 조합.
- 실패하거나 오래 걸리면 즉시 폴백(자동 지형 → 기본 테마)으로 그립니다. 로딩 때문에 장면이 늦어지지 않습니다.
- 사진 방식이면: 장당 100~300KB × 3,000 = 300~900MB. 저장소와 Pages 한도에 막힙니다. 매주 교체하면 Git 기록이 연 수 GB~15GB씩 쌓입니다 [추측: 100KB × 3,000 × 52]. **사진 방식은 이 규모에 부적합.**

### (5) 유지보수
- 명소 정보 오류(철거·이름 변경)는 데이터 한 줄 수정.
- 부품 코드는 한 곳이라 장면 수정 시 같이 시험.
- `source`(출처)·`confidence`(신뢰도)·`status`(초안/확인됨) 필드로 "확인 안 된 것"을 분리. 어드민에서 초안만 골라 검토.
- 공공누리 출처 표시는 `credits` 필드로 자동 모음.

## 15. 일주일 교체가 정말 필요한가
- 필요하지 않다고 봅니다 [추측: 제 판단]. 방문자는 지역 간 이동이 목적이고, 배경을 매주 다른 장소로 바꾸면 "그 지역의 상징"이라는 의미가 흐려지고, 비용만 커집니다.
- 구분:

| 종류 | 무엇이 바뀌나 | 새 자료 필요? | 비용 |
|---|---|---|---|
| 시즌 | 은행잎·벚꽃·눈·초록(월 기준; 현재 은행잎 코드가 있음 [확인]) | 없음(코드) | 0 |
| 날씨 | 안개·비 (지역 결정적 난수, 실제 기상 API는 쓰지 않음, D-01) | 없음 | 0 |
| 시간대 | 낮·노을·밤 (현재 `setTime` 있음 [확인]) | 없음 | 0 |
| **주간 순환** | 그 지역 명소 후보(2~3개) 중 이번 주 대표를 `주차 번호 % 개수`로 선택 | 후보를 처음에 넣어 두면 끝 | 0 |
| 새 명소 교체 | 데이터를 새로 넣음 | 사람·Claude 작업 | 있음, 분기 단위 권장 |

- 권장(P-21): "교체"는 **주차별 순환(자동)** + 시즌·날씨·시간대 변주. 새 명소 추가는 필요할 때 수시로.
- 지역당 후보가 1개뿐이면 순환은 의미가 없으므로, 시/도 단계에서는 2~3개씩 넣는 것을 권장.

| `Scene.build()` 끝 (1368~1370줄) | `buildAlley/Market/Park` 호출 | 그 뒤에 `buildBackdrop(E, r, lm)` 추가. 환경 그룹 `E`에 넣으므로 `clearEnv()`가 지역을 옮길 때 자동 정리됨 [확인: 1323줄] |
| `setTime` (1565줄) | 해·안개 | 실루엣 재질이 안개·밤 색을 따르도록 같은 조명 사용 (추가 변경 없음) |
| 이름표(`pUp`/`pDong` 등) | 지역 이름 | 명소 이름 한 줄 표시("근처 명소: 오이도") 추가 |

## 18. 어드민 기능 제안 (R-15 9장 "시간·장면" 구역 확장)
- 명소 미리보기: 지역 선택 → 명소 후보 목록 → 눌러서 즉시 배경 교체(저장 없이 시험).
- 교체: 이번 주 대표를 강제 지정 / 주차 순환 켜기·끄기.
- 상속 표시: 지금 보는 지역의 값이 동/시군구/시/도/자동 중 어디서 왔는지 라벨.
- 지도: 채운 곳 / 상속 중인 곳 색 구분, `draft` 개수.
- 입력 도우미: 이름 + 유형 선택 + 한 줄 설명을 붙여 넣으면 JSON 조각을 만들어 줌(복사해 Claude에게 전달 또는 파일에 붙임).
- 부품 미리보기: 유형 15종 한 줄 나열, 색·높이 슬라이더, 낮/노을/밤/안개 전환.
- 성능: 배경 켜기/끄기와 초당 프레임 비교, 저사양 시 2D 카드(B) 강제.
