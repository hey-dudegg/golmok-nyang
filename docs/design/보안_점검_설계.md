## 2. 헤더와 CSP

### 2-1. 1차 `_headers` 문안 (0장 A-1, A-3 반영)
```
/*
  Cache-Control: no-cache
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(), microphone=(), geolocation=()
  X-Frame-Options: DENY
  X-Robots-Tag: noindex
```
- `X-Frame-Options: DENY`는 배포_계획 초안에 없던 것(클릭재킹 방지). 다른 사이트에 끼워 넣을 계획이 없다면 추가.
- `X-Robots-Tag: noindex`는 시험 기간용(4장). 정식 공개 때 이 줄만 지움.

### 2-2. CSP (2차)
- 배포_계획 5장 CSP 초안을 쓰되, 먼저 Report-Only로 1~2주 시험, 위반 0건이면 강제.
- 인라인 importmap·로더 때문에 강제하려면 로더를 외부 파일로 빼야 함(S-8). developer 작업.
- 3-3의 `?admin` 노출·`style-src 'unsafe-inline'`은 당분간 허용(스타일 속성 사용).
- 로그인 제공자(카카오·Google) 이동은 페이지 이동 방식이면 `connect-src` 추가가 필요 없을 수 있음 [미확인: 구현 방식에 따라].

## 3. 코드 점검 결과 (읽기만, 수정 없음)

### 3-1. XSS: `innerHTML` 사용처 분류
- 고정 아이콘 문자열(`ICON.*`)만 넣는 곳: main.js(잠금 표시), board.js, card.js, picker.js, share.js, feedback.js, names_panel.js. 문제 없음.
- 숫자를 문자열로 끼워 넣는 곳: names_panel.js 49·51줄(`n.score`, `n.dislikes`), board.js 91·92줄(좋아요·댓글 수). **지금은 숫자지만, 2차에서 서버 값이 들어오면 문자열일 수 있음.** 조치: 숫자 변환(`Number()`) 또는 `textContent`로 바꿀 것(developer 제안).
- 사용자 글·닉네임·이름·의견은 `h(..., { text })`·`textContent`로 넣고 있음(names_panel 59줄, feedback_admin 23줄 등에서 확인). feedback.js 첫 줄에 "innerHTML 금지" 규칙이 적혀 있음.
- 조치: 2차 전 reviewer가 이 목록을 기준으로 전수 확인. 새 `innerHTML`에 사용자 값이 들어가면 상 등급으로 올림. 시험으로 고정하려면 tester가 "src에서 innerHTML 줄이 `ICON.` 또는 숫자 변수만 쓰는지" 정적 검사 추가 제안.

### 3-2. 시험용 전역 노출 (main.js 끝)
- `window.__app`, `window.__advance`는 항상 노출. 나머지 `__trips`·`__inter`·`__recipe`·`__pose`·`__lm`은 `?admin`일 때만.
- 영향: 1차에서는 서버가 없어 이 브라우저 안 상태만 바뀜(낮음). 2차에서는 서버 규칙(RLS·RPC)이 막아야 하며, 화면 값은 신뢰하지 않음.
- 조치: 운영(비로컬) 호스트에서는 `__app`·`__advance`를 노출하지 않거나 `?test`+로컬에서만 노출. 시험(tests/)이 의존하므로 tester 확인 후 변경. 담당 developer, 2차 전.
- `?admin`으로 `__*`가 열리는 것은 어드민 보호가 아님(서버 검증이 보호). 8장 참고.

### 3-3. 로컬 모의 조건
- `LocalMock.usable()`은 호스트 이름이 localhost 계열일 때만 true(local_mock.js 8줄). 운영 도메인은 해당 없음. 호스트 목록에 운영 도메인이 들어가지 않는지 시험으로 고정(tester).
- `Admin.wantsPage`는 URL에 `admin`이 있는지만 봄(gate.js 14줄). 활성화(`active`)는 소유자 확인 뒤에만 켜져야 함. 운영 어댑터 구현 시 이 확인이 서버 값(admins 표)을 따르는지 reviewer가 본다.

### 3-4. 외부 로딩

## 4. 봇·AI 크롤러와 전체 공개(D-38)

### 4-1. 전체 공개와 검색 노출의 관계
- D-38은 "검색 노출 포함 전체 공개, 단 보안 검토 통과 후". 즉 검색 노출은 **보안 검토 통과 뒤**에 켜는 것으로 읽는 것이 안전함.
- "AI 학습용 크롤러 차단"과 "검색 노출"은 별개로 다룬다. 검색 엔진은 허용하고 AI 학습·수집 봇만 막는 조합이 가능.
- 주의: robots.txt는 **부탁**일 뿐 강제력이 없음. 지키지 않는 봇에는 Cloudflare 쪽 차단이 필요(6장). 또한 robots.txt로 막은 주소에는 noindex 표시를 읽을 수 없으므로, 검색 엔진용 noindex는 robots.txt 차단과 섞지 않는다(검색 봇은 robots에서 허용하고 헤더로 noindex).

### 4-2. 단계별 권장안
| 시기 | 검색 엔진 | AI 크롤러 | 방법 |
|---|---|---|---|
| 1차·시험 기간(D-41, 약 30일·100명) | 비노출 | 차단 | `X-Robots-Tag: noindex` + robots.txt에서 AI 봇만 Disallow |
| 정식 전체 공개(D-38, 보안 검토 통과 뒤) | 노출 허용 | 차단 유지 | noindex 줄 제거, robots.txt 유지, 사이트 설명 메타(`description`) 추가 |

- 이유: 시험 기간에는 이웃 100명에게 링크로 알리는 것이 목적이고, 공개 전 점검·개인정보 고지가 끝나지 않은 상태에서 검색에 올라가면 되돌리기 어려움(검색 결과·캐시에 남음).
- 사용자 결정 필요: 정식 공개 시점의 검색 노출 여부를 D-38 그대로 확정할지(N-1, 11장).

### 5-4. 고지 문구 (사용자 검토 후 사용, 법적 판단 아님)
- 1차 첫 화면 한 줄: "이 앱은 이 기기(브라우저)에만 정보를 저장하고, 서버로 보내지 않아요. 글꼴·3D 부품은 외부에서 받아와요."
- 2차 로그인 직전: 수집 항목, 목적, 보관 기간, 제3자, 삭제 요청 방법, 만 14세 미만 안내를 한 화면 요약 + 상세 페이지 링크.
- 안내 페이지에는 운영자 연락 수단이 필요함. 개인 메일을 쓰지 않으려면 의견 보내기 화면을 연락 수단으로 지정(비용 0, 개인정보 최소).

## 6. Cloudflare 무료 기능 활용 (사용자가 설정, D-14, 모두 무료 범위 [미확인: 요금제 변경 가능성])
1. Pages 기본 도메인에서 시작. 커스텀 도메인은 유료(도메인 비용)라 지금은 제안만 → 대안: 기본 `*.pages.dev` 주소 사용.
2. 계정 보안: 2단계 인증, API 토큰 만들지 않기.
3. 봇 관련: "AI 크롤러 차단" 및 "Bot Fight Mode" 계열 무료 옵션을 켠다. 해당 옵션은 **커스텀 도메인(존)에 붙는 기능**이라 `pages.dev`만 쓸 때는 쓸 수 없을 수 있음 [미확인]. 이 경우 robots.txt와 `_headers`가 유일한 방어이며, 지키지 않는 봇은 막지 못한다는 점을 받아들인다.
4. 공격 요청 제한(속도 제한)은 정적 파일에는 실익이 작음. 2차의 DB 호출 제한은 Supabase 쪽 RPC 제한(7장)이 중요.
5. 켠 뒤 시크릿 창에서 사이트가 정상 열리는지 확인(봇 차단 옵션이 시험 브라우저를 막지 않는지).

## 7. Supabase 2차 점검 (RLS)

### 7-1. 원칙
- 모든 표 RLS 켬. 정책 없으면 접근 불가. 공개 anon 키만 코드에 둠(D-11). service_role은 어디에도 쓰지 않음.
- 클라이언트 쓰기는 "자기 uid 행"만. 규칙이 있는 쓰기(투표·신고·의견·홍보)는 RPC(서버 함수)로만.
- 1-4 초안에서 보강할 점(developer·tester 검토):
  1. `members_read using (true)`: 닉네임·홈 지역·가입 시각이 **전체 공개**. 필요 열만 보이는 보기(view)로 줄이거나 `home`·`age_ok`는 본인만 읽게 분리.
  2. `names2`·`name_votes`·`feedback` 표에도 `enable row level security`를 명시(초안 코드에는 `members`·`posts`·`feedback`만 보임).
  3. `posts.img`는 길이 제한만 있음. 형식(`data:image/...`)과 크기를 check로, 게시글 속 링크 차단은 서버에서도.
  4. `posts_insert`는 uid만 확인. 서버 쪽 쓰기 속도 제한(회원당 분당 N건)이 필요(스팸·한도 소진 방지).
  5. `security definer` 함수는 `search_path`를 고정하고 필요한 사용자에게만 `execute` 권한(공개 함수 목록에 노출되는 점 주의).
  6. 익명 로그인 사용 시 `not is_anonymous()` 검사가 회원 전용 쓰기(게시·홍보·츄르)에 일관되게 적용되는지.

### 7-2. 놓은 상자 이웃 공유(D-39)
- 읽기: 같은 동네 상자만 조회(`region` 조건)하되 전체 읽기 허용도 데이터가 작아 허용 가능. 쓰기: 회원만, 자기 uid, 동네당 개수·회원당 개수 제한, 위치는 동네 안 격자값 범위 check.
- 상자에 글(메시지)을 허용하면 게시판과 같은 글자 정리·링크 차단·길이 제한을 서버에도 적용. 글 없이 모양·위치만이면 개인정보 위험이 거의 없음(권장 시작).
- 실시간 방송은 위조 가능(S-14): DB 변경 구독(RLS가 적용되는 방식)을 쓰고, 클라이언트 직접 방송은 쓰지 않는 방안을 우선 검토.
- 신고·삭제: 어드민 삭제 도구 필요. 상자를 놓는 시간 간격은 D-40 계열 서버 규칙.

### 7-3. 시험 항목 (tester, 2차)
- 로그인 없이·익명으로·회원으로·비관리자 회원으로 각각 모든 표의 읽기·쓰기를 시도해 기대 결과와 비교하는 표를 만든다(결과는 통과/실패만 기록, 방법 상세는 비공개 노트).
- 다른 사람 uid로 쓰기, 남의 글 삭제, 어드민 표·`app_config` 쓰기, 의견 읽기가 모두 거부되는지.

## 8. 어드민은 본인만

원칙: 화면의 `?admin`·`isOwner`는 버튼 표시용. **서버(RLS·`is_admin()`)가 진짜 방어**. 주소 숨기기는 보안으로 보지 않음.

### 8-1. 1차(정적, 로그인 없음)
- 현재 코드: 운영 주소에서는 `Caps.user=null`이라 어드민 패널이 열리지 않음(0-1, S-3). 어드민 화면이 만드는 **서버 데이터가 없어** 지킬 대상이 거의 없음.
- 남는 위험: 어드민 JS 코드와 `__*` 도구가 모든 방문자에게 다운로드됨(정적 파일). 내용은 설정 화면·레시피 도구 수준이며 비밀이 없어야 함 → 어드민 모듈에 비밀·개인정보·내부 설명을 쓰지 않음(reviewer 확인).
- 어드민 기능 확인이 필요한 사용자는 **로컬 서버**(`localhost`)에서 `?admin`으로 여는 것을 공식 경로로 둔다(`LocalMock`이 소유자로 인정). 운영 주소 쪽 어드민 우회 경로(쿼리·저장값·콘솔)를 만들지 않는다.
- 1차에서 하지 말 것: 비밀번호·암호를 코드에 넣어 어드민을 여는 방식(번들이 공개되어 의미 없음), 주소만 숨기는 방식.
- Cloudflare Access(무료 최대 50명) 같은 접근 통제는 어드민이 별도 경로·도메인일 때만 가능하고 현 구조(한 페이지)에 맞지 않음 → 사용하지 않음.

### 8-2. 2차(Supabase)
1. 사용자가 로그인(카카오 또는 Google)한 뒤, 대시보드 SQL 편집기에서 **본인 uid를 직접** `admins` 표에 넣는다. uid는 저장소·문서·LOG에 쓰지 않는다. 사용자 단계.
2. `admins` 표는 RLS 켜고 정책 없음(클라이언트 읽기 불가). 화면은 `is_admin()` RPC가 true를 줄 때만 `Admin.active`를 켠다.
3. 어드민 전용 쓰기(`admin_kv`, `app_config`, 글·이름 삭제, 의견 읽기, 상자 삭제)는 모두 `is_admin()` 정책 또는 RPC 안 검사. 화면 값은 신뢰하지 않음.
4. 제공자 계정이 곧 관리자 열쇠이므로: 해당 카카오·Google 계정에 2단계 인증 필수. 관리자를 한 명(1행)으로 유지.
5. 새 로그인 제공자·익명 로그인이 `admins` 행과 우연히 연결되지 않는지 확인(uid로만 대응, 이메일 일치로 관리자 판정하지 않음).
6. 이메일 검증 없이 가입 가능한 제공자를 추가하면 "같은 이메일 계정 연결"이 일어날 수 있으므로, 계정 자동 연결 설정은 끈다 [미확인: Supabase 설정 항목 이름].
7. 시험: 비관리자(회원·익명·비로그인)로 `?admin`을 열어 패널이 안 열리고, 개발자 도구로 어드민 쓰기를 직접 호출해도 서버가 거부하는지. 관리자 본인은 되는지.
8. 어드민 세션이 오래 남지 않도록 로그아웃 버튼을 두고, 공용 기기에서 열지 않기. 사용자 습관 안내.
