권장 순서:

### 1-4. 표와 RLS 정책 초안

RLS(행 수준 보안)는 "주소와 anon 키가 공개돼도, 표마다 누가 읽고 쓸 수 있는지를 DB가 직접 막는" 장치입니다. **모든 표에 RLS를 켜고, 정책이 없으면 아무도 못 하게** 시작합니다. 아래는 초안이며 적용 전 developer·tester 검토가 필요합니다. 값(주소·키)은 들어 있지 않습니다.

```sql
-- 관리자: 사용자가 대시보드에서 본인 uid를 직접 넣는다(저장소에 uid를 적지 않는다)
create table admins (uid uuid primary key references auth.users on delete cascade);
alter table admins enable row level security;            -- 정책 없음 = 클라이언트는 읽기·쓰기 불가
create function is_admin() returns boolean language sql security definer stable
  as $$ select exists (select 1 from admins where uid = auth.uid()) $$;

create table members (
  uid uuid primary key references auth.users on delete cascade,
  nick text not null check (char_length(nick) between 1 and 12),
  home text, age_ok boolean not null default true, joined_at timestamptz not null default now());
alter table members enable row level security;
create policy members_read  on members for select using (true);            -- 닉네임은 공개(게시판 표시용)
create policy members_write on members for insert with check (uid = auth.uid() and not is_anonymous());
create policy members_edit  on members for update using (uid = auth.uid());
-- is_anonymous(): (auth.jwt()->>'is_anonymous')::boolean 를 감싼 작은 함수 [추측: 클레임 이름은 만들 때 확인]

create table posts (
  id uuid primary key default gen_random_uuid(),
  uid uuid not null references members(uid) on delete cascade,
  nick text not null, body text not null check (char_length(body) <= 500),
  img text check (img is null or char_length(img) <= 60000),       -- 사진은 작게(7장 위험 R-2)
  created_at timestamptz not null default now());
alter table posts enable row level security;
create policy posts_read   on posts for select using (true);
create policy posts_insert on posts for insert with check (uid = auth.uid());   -- 회원만(D-16)
create policy posts_delete on posts for delete using (uid = auth.uid() or is_admin());
-- post_likes(post_id, uid) / post_comments(...): 같은 방식. uid = auth.uid() 만 넣기·지우기, 댓글 길이 제한

create table names2 (
  id uuid primary key default gen_random_uuid(),
  region text not null, name text not null check (char_length(name) between 1 and 8), -- 길이는 NAME_RULE.MAXLEN과 맞춘다
  uid uuid not null, nick text, created_at timestamptz default now(), gone boolean default false);
create table name_votes (                                   -- 세션(uid)마다 이름 1개당 1행
  name_id uuid references names2 on delete cascade, uid uuid,
  vote text check (vote in ('up','down')), reported boolean not null default false,
  primary key (name_id, uid));
-- 읽기: 모두. 쓰기: 클라이언트 직접 쓰기 금지, RPC name_propose / name_vote / name_report 만.
-- RPC 안에서: 세션당 5개 제한(D-31), 좋아요·싫어요 배타, "싫어요>좋아요 또는 신고 5" 이면 gone=true 를 서버가 계산

create table feedback (
  id uuid primary key default gen_random_uuid(), uid uuid, title text, from_name text, body text,
  created_at timestamptz not null default now(),
  constraint fb_len check (char_length(title) <= 40 and char_length(coalesce(from_name,'')) <= 40 and char_length(body) <= 500));
alter table feedback enable row level security;
create policy fb_admin_read on feedback for select using (is_admin());          -- 넣기 정책 없음. RPC(feedback_submit)만 넣는다
-- feedback_submit: 같은 uid가 60초에 1회·하루 5회 초과면 거부(서버 시각 기준 → 시계 되돌리기 무력화)

create table promo_lock (key text primary key, holder text, until timestamptz not null default now(), data jsonb);
insert into promo_lock(key) values ('promo');
create function promo_try(p_holder text, p_ttl_ms int, p_data jsonb) returns boolean
language plpgsql security definer as $$
declare n int; begin
  if not exists (select 1 from members where uid = auth.uid()) and not is_admin() then return false; end if;   -- 회원 전용
  update promo_lock set holder=p_holder, data=p_data, until = now() + (p_ttl_ms || ' ms')::interval
   where key='promo' and until < now();                      -- 만료됐을 때만 갱신 = 원자적으로 한 명
  get diagnostics n = row_count; return n = 1; end $$;
-- 확인 필요: 같은 uid 1분 쿨다운, app_config 의 최소 간격(한도 임박 시 서버가 늘림), 방송까지 DB 안에서 보내기(realtime.send)

create table app_config (key text primary key, value jsonb);   -- 읽기 모두, 쓰기 어드민(홍보 최소 간격, 사람 수 숨김 스위치 등)
create table admin_kv (key text primary key, value jsonb);     -- 어드민 전용(레시피)
-- bonds(uid pk, data jsonb, 크기 제한), post_likes, post_comments, 사용량 집계표 usage_counter 는 개발 때 같은 패턴으로
```

악용 방지 요약:
- **신고·투표**: 서버 RPC가 규칙을 계산하므로 화면 코드를 고쳐도 규칙을 못 바꿉니다. 다만 "세션 여러 개"는 막지 못합니다(7장 S-5).
- **세션 식별**: 로그인 안 한 사람도 **익명 로그인**(Supabase 기능, 대시보드에서 켬)으로 uid를 받습니다. 현재 코드는 `uid`가 없으면 db를 끄는 구조(`initCaps`)라 익명 로그인이 필요합니다. 브라우저 데이터를 지우면 새 uid가 됩니다 [확인: 공식 문서 요약].
- **홍보 한 명만**: 위 `promo_try`의 조건부 UPDATE. 100명이 동시에 눌러도 DB가 한 줄씩 처리해 1명만 true.
- **관리자 판정**: 화면의 `isOwner`는 버튼을 보이게 하는 용도일 뿐, **진짜 방어는 `is_admin()` RLS**입니다.

### 1-5. 무료 한도 계산

가정(모두 [추측]): 한 방문 5분, 한 방문에 지역 3곳 이동, 동시 접속은 하루 평균의 약 2.5배가 최고, 사람의 30%가 가장 붐비는 지역에 몰림.

**(a) 동시 접속 200명**
- 브라우저 탭 1개 = 실시간 연결 1개. 탭을 열어 두고 잊은 사람도 자리를 차지합니다.
- 대비: 탭이 1분 이상 숨겨지면(`document.hidden`) 연결을 끊고 돌아오면 다시 연결 → 자리 낭비 방지. 200 초과로 연결이 거부되면 `room.live=false`로 사람 수·홍보만 끄고 나머지는 그대로(설계안 10장과 같음).
- 대략: 하루 방문 약 3,000명(평균 5분) → 평균 동시 약 10명, 최고 약 50명 [추측]. 200 동시는 하루 방문 1만 명 안팎입니다.

**(b) 실시간 메시지 월 200만 건 (받는 쪽까지 센다고 가정)**

| 시나리오 | 사람 수 알림(지역 Presence) | 홍보 알림 | 합계/월 | 한도 대비 |
|---|---|---|---|---|
| 시험 소규모: 하루 방문 100, 평균 동시 10, 홍보 하루 20회 | 100×30일×6이벤트×지역 3명 ≈ 5.4만 | 20×10명×30 ≈ 0.6만 | 약 6만 | 3% |
| 시험 중간: 하루 600, 평균 동시 40, 홍보 하루 100회 | 600×30×6×지역 12명 ≈ 130만 | 100×40×30 ≈ 12만 | 약 142만 | 71% (주의) |
| 큰 시험: 하루 1,500, 평균 동시 80, 홍보 하루 500회 | 1,500×30×6×지역 24명 ≈ 650만 | 500×80×30 ≈ 120만 | 약 770만 | 385% (초과) |
| 최악: 홍보가 10초마다 계속, 동시 40명 | - | 8,640×40×30 ≈ 1,040만 | 1,040만+ | 초과 |

(이벤트 6 = 방문 1회에 지역 3곳 입장·퇴장 / 계산은 근사입니다.)

해석: **사람 수(Presence)가 가장 큰 소비처**입니다. 대비책 3단계:
1. 처음부터: 지역마다 채널 분리(이미 설계), 사람 수 표시 갱신을 화면에서 1~2초로 묶기, 탭 숨김 시 연결 해제.
2. 서버 한도(app_config): `promo_try`가 사용량 집계표를 보고 월 150만 건이 가까워지면 홍보 최소 간격을 10→30→60초로 늘리거나 "오늘은 홍보 쉬어요"로 거부.
3. 그래도 모자라면: Presence를 "30초마다 RPC로 지역별 인원 읽기"로 바꿉니다. **`count/onCount` 모양은 그대로**라 화면 변경이 없습니다(실시간 메시지를 거의 안 씀, 대신 DB 요청 증가).

**(c) DB 500MB**

| 데이터 | 한 건 크기 [추측] | 예상량 | 합계 |
|---|---|---|---|
| members | 약 0.3KB | 회원 1,000명 | 0.3MB |
| bonds | 약 3KB(고양이 16마리 기록) | 1,000명 | 3MB |
| names2 + name_votes | 약 0.5KB + 0.1KB | 16곳 × 300개 | 약 3MB |
| feedback | 약 1KB | 90일 보관, 하루 20건 | 약 2MB |
| **posts(사진 포함)** | 최대 약 190KB(지금 코드 상한), 새 기준 60KB 이하 권장 | 상한 300개 유지 시 | 최대 약 57MB(옛 기준 60KB 기준 18MB) |
| 합계 | | | 약 30~70MB → 500MB의 6~14% |

사진을 DB 안(base64)에 두면 가장 큽니다. 최근 N개만 남기는 정리를 두면 안전합니다.

**(d) 전송량 5GB — 게시판이 위험 (R-2)**
지금 `Board`는 글 60개를 한 번에 읽습니다. 글마다 사진이 최대 약 190KB면 **한 번 열 때 최대 약 11MB**. 한 달 5GB ÷ 11MB ≈ **약 450번 열면 끝**입니다 [추측: 최악 기준, 평균은 이보다 작음]. 조치: 목록은 글 20개 + 작은 미리보기(20KB 이하)만 읽고 큰 사진은 눌렀을 때 읽기 / 또는 Supabase Storage(공개 버킷, 캐시 전송량 5GB 별도)로 옮기기. 선택은 developer 설계 때 정합니다(사용자 결정 아님).

**(e) 90일 보관 정리 방법 (D-09 연결)**
- 하루 한 번 GitHub Actions가 Supabase에 요청합니다(정지 방지, D-09). 이 요청을 **`daily_cleanup()` RPC 호출**로 만들면 같은 요청이 정리도 합니다: 90일 지난 feedback 삭제, 오래된 posts·이름 삭제 표시 정리, 사용량 집계 갱신.
- 이 함수는 "지울 게 있으면 지우고 아니면 아무것도 안 하는" 안전한 함수라 anon 키로 불러도 위험이 작습니다(허용 대상은 이 함수 하나만, 실행 횟수는 의미 없음).
- 대안 [미확인]: Supabase의 pg_cron 확장(무료에 포함되는지·설정 방법은 이번에 확인 못 함). Actions 방식이 D-09와 일치하고 설정이 단순합니다.
- Web3Forms 쪽 메일 보관은 서비스 정책(30일 기록)이라 우리가 지울 수 없음 → 개인정보 안내에 적습니다.

## 2. P-07 먼저: anon 키를 "빌드 없는" 정적 파일에 넣는 방법

**안전성:** Supabase의 anon(공개) 키는 **브라우저에 있어야 동작하는 열쇠**입니다. 어떤 방식으로 주입하든 방문자는 개발자 도구에서 볼 수 있습니다. 그래서 키가 비밀이어서가 아니라 **RLS(1-4)가 모든 표에 켜져 있고 정책이 맞아야 안전**합니다. 지켜야 할 것은 **관리자 키(service_role·secret 계열)를 어디에도 넣지 않는 것**(D-11)입니다. Supabase가 최근 "publishable/secret" 키 체계를 내놓았다는 기억이 있으나 [미확인] 대시보드에 보이는 "공개용(anon 또는 publishable)" 키 하나만 쓰면 됩니다.

| 항목 | A. `config.js`에 공개 값을 커밋 | B. 배포 때 환경 변수로 치환 |
|---|---|---|
| 방식 | `src/config.js`에 주소·공개 키를 직접 적고 커밋 | Pages 빌드 명령(예: 파일 문자열 치환 스크립트)이 환경 변수를 `config.js`에 써 넣음 |
| 빌드 없음(D-13) | 유지 | **빌드 명령이 생김**(작지만 D-13 취지에 어긋남, Node/쉘 환경 의존) |
| 저장소 노출 | 키가 공개 저장소에 보임 → 스캐너가 경고를 낼 수 있음(공개 키라 실제 위험은 아님) | 저장소에는 없음, 단 방문자에게는 똑같이 보임 |
| 방문자 노출 | 동일 | 동일 |
| 스테이징/운영 분리 | `config.js` 안에서 **접속 주소(hostname)로 고름**(운영 도메인이면 운영 값, 그 외 `*.pages.dev`면 스테이징 값). 빌드 불필요 | 환경마다 값을 따로 대시보드에 입력(Pages는 운영/미리보기 환경 변수 분리 지원 [미확인: 이번 문서 확인 못 함]) |
| 로컬 시험 | 같은 파일, 주소가 localhost면 모의 | 로컬 전용 값 파일 별도 필요 |
| 사용자 작업 | 값 2개를 `config.js`에 붙여 달라고 개발자에게 전달 | 대시보드에 환경 변수 입력 + 빌드 설정 |
| 키 교체 | 파일 수정 + 재배포(1분) | 대시보드 수정 + 재배포 |

**권장: A.** 이유: 키는 어차피 공개되고, 진짜 방어선은 RLS이며, 빌드 없음(D-13)을 지킵니다. 비밀이 아님을 파일 머리 주석에 명시하고, `/secure-check`에 "service_role·secret 문자열이 없는지" 검사를 추가합니다. 위험이 하나 있어요: 스캐너 경고가 오면 사용자가 놀랄 수 있으니 미리 안내합니다(이 문서가 안내). Web3Forms 접근 키도 같은 방식(공개용)입니다.
스캐너 경고를 정말 피하고 싶을 때만 B를 선택합니다. B로 가면 작업량이 +1회(빌드 스크립트와 테스트).

**결정 요청 번호 P-07 → 3장.**

## 4. 이웃 데이터(P-15) 처리 방안 비교

현황: 회원(`members`), `data/users`(유대), `posts`(게시글), `names`(옛 이름 투표)가 원본 아티팩트 db에만 있고 저장소에는 없습니다. 이름 투표는 D-20·D-31로 이미 "새로 시작(옛 기록은 읽지 않음)"이므로 사실상 대상은 **회원·유대·게시글**입니다.

핵심 사실 두 가지:
1. 옛 회원의 uid는 **아티팩트(Claude 계정) 기준 식별자**라 새 로그인(카카오 등)의 uid와 연결되지 않습니다. 따라서 회원·유대·"내 글 삭제 권한"은 **사람에게 이어 줄 방법이 없습니다**(글 내용만 옮길 수 있음). [추측: 아티팩트 `user.id()`의 형태를 확인하지 못함]
2. 다른 사람이 쓴 글·사진·닉네임을 동의 없이 새 공개 서비스로 옮기는 것은 개인정보 측면에서 부담이 있습니다. 법률 자문은 아니며 안내문·동의 문제를 사용자가 판단해 주세요.

| 선택 | 하는 일 | 영향·위험 | 작업량 |
|---|---|---|---|
| A 옮기기 | 아티팩트 db를 내려받아(방법 [미확인]: 아티팩트 db를 읽는 도구가 이 환경에서 되는지 확인 필요) 변환 → Supabase에 넣음. 회원은 닉네임만 "이름 없는 옛 이웃"으로, 글은 작성자 표시만 보존 | 이어지는 것 거의 없음(위 1). 동의 없는 이전(위 2). 변환·검증 작업 큼, 실패하면 일부 데이터 오염 | 개발 1~2회(약 10만~30만 토큰 [추측]) + 사용자 확인 |
| B 버리기 | 옛 아티팩트는 그대로 두고 방치, 새 서비스는 빈 상태 | 가장 단순. 옛 데이터는 아티팩트가 살아 있는 동안만 존재(아티팩트 삭제·정책 변경 시 소멸) | 없음 |
| C 보관 | B에 더해, 가능하면 **내보내기 사본(JSON)을 저장소 밖(비공개)에 보관**. 새 서비스는 새로 시작. 필요해지면 나중에 A | 사본에 타인의 닉네임·uid·사진이 있으므로 **공개 저장소에 올리지 않음**(.gitignore된 .private 폴더도 오조작 위험이 있어 저장소 밖 권장) | 사용자 1회 + 에이전트 0~1회 |

**권장: C.** 이유: 이어 붙일 신원 연결이 없어 옮겨도 얻는 것이 적고, 동의 문제가 있으며, 새 시작이 D-20·D-31 방향과 같습니다. 사본은 보험입니다. 사본 가능 여부는 [미확인]이라 실패하면 B가 됩니다.

### CSP 초안 (적용 전 시험용, 값의 `<프로젝트>`는 자리표시)

```
/*
  Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'sha256-<로더 해시>' 'sha256-<import map 해시>'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' https://<프로젝트>.supabase.co wss://<프로젝트>.supabase.co https://api.web3forms.com; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Permissions-Policy: camera=(), microphone=(), geolocation=()
```
- three.js·supabase-js를 자체 호스팅하면 `script-src`에 외부 주소를 넣을 필요가 없습니다(자체 호스팅 권장 이유).
- 아직 CDN을 쓴다면 `https://cdn.jsdelivr.net`을 `script-src`에 추가.
- `style-src 'unsafe-inline'`: 코드가 스타일 속성을 쓰므로 필요할 가능성이 큼 [추측].
- Cloudflare Web Analytics(D-12)를 켜면 해당 스크립트·전송 주소도 허용해야 합니다(주소는 켠 뒤 확인) [미확인].
- 시험 기간에는 Report-Only로 위반을 브라우저 콘솔에서 확인, 위반 0건이 되면 강제로 전환합니다.
- 공개 시 `noindex`(P-02 A) 헤더: `X-Robots-Tag: noindex`를 같은 규칙에 추가.

**테스트 방법과 스테이징:**
- 스테이징 = 별도 Supabase 프로젝트(무료 2개 중 하나) + Cloudflare Pages의 `staging` 브랜치 미리보기 주소. 한 프로젝트를 쪼개 쓰지 않는 이유는 실수로 운영 데이터를 건드리지 않기 위해서입니다. 단, 무료 활성 프로젝트가 2개이므로 다른 프로젝트가 이미 있으면 정지하거나 삭제해야 합니다.
- 기준: tests/ 전부 통과 → RLS 시험(로그인 없이·다른 사람 계정으로 쓰기 시도가 거부) → 2대 기기 실시간 확인 → 한도 시뮬레이션(동시 연결 수·메시지 수 로그).
- 운영 시험(P-05): 링크 공유 20~30명, 2주. 매주 확인: 월 메시지·DB 크기·전송량(대시보드 사용량 화면), 의견 메일, 신고·삭제 이상 징후.

**사용자 작업 체크리스트** (비전문가용, 한 줄씩 따라 하기. 화면 이름은 바뀔 수 있습니다 [미확인]. 중간에 막히면 화면을 설명해 주세요)

A. 계정·프로젝트 (M4-1)
1. 사용하는 3개 서비스(GitHub·Cloudflare·Supabase) 계정에 **2단계 인증**을 켠다. 비밀번호는 비밀번호 관리자에 저장한다.
2. Cloudflare에 가입(무료). 결제 수단은 **등록하지 않는다**.
3. Supabase에 가입(무료)하고 새 프로젝트 2개를 만든다: `golmok-staging`, `golmok-prod`(이름은 자유, 실명·회사명 금지). 지역은 가까운 곳(서울이 있으면 서울 [미확인]). **DB 비밀번호는 만들어서 비밀번호 관리자에만 저장**한다(채팅·저장소 금지).
4. 각 프로젝트의 "Project Settings → API"에서 **Project URL**과 **공개용(anon 또는 publishable) 키**만 복사해 개발자에게 전달한다. `service_role`·`secret`이라고 적힌 키는 **복사도 전달도 하지 않는다**.
5. GitHub 저장소가 이미 있으므로 Cloudflare Pages에서 "Connect to Git"으로 저장소를 연결한다.

B. 데이터베이스 준비 (M4-2)
1. 개발자가 준 SQL 파일 내용을 스테이징 프로젝트의 **SQL Editor**에 붙여 넣고 Run 한다(오류가 나면 화면을 복사해 알려 주기).
2. 본인 계정으로 한 번 로그인한 뒤 "Authentication → Users"에서 본인 **User UID**를 복사해, 개발자가 준 `insert into admins ...` 한 줄에 넣어 SQL Editor에서 실행한다(이 uid는 저장소에 적지 않는다).
3. "Authentication"에서 **Anonymous sign-ins**를 켠다.

C. 로그인 (M4-3, P-01)
1. 카카오 디벨로퍼스에서 앱 1개 생성 → 카카오 로그인 활성화 → **Redirect URI**에 Supabase가 알려 주는 주소 등록 → 동의 항목은 **닉네임만**.
2. REST API 키(와 Client Secret)를 Supabase "Authentication → Providers → Kakao"에 붙여 넣는다(저장소·채팅에 쓰지 않음).
3. Supabase "Authentication → URL Configuration"의 허용 주소에 스테이징·운영 사이트 주소를 넣는다.
4. (P-01 A를 고르면) Google Cloud 콘솔에서 같은 방식으로 OAuth 클라이언트를 만들고 Supabase에 붙여 넣는다.

D. 의견 메일 (M4-5)
1. Web3Forms에서 받을 이메일을 입력해 **접근 키**를 받는다(메일 주소는 이 사이트에만 입력, 저장소 금지).
2. 접근 키를 개발자에게 전달한다(공개용). 허용 도메인 설정이 있으면 우리 사이트 주소로 제한한다.
3. 배포 후 의견을 1건 보내 메일이 도착하는지 확인한다.

E. 배포 (M4-6)
1. Cloudflare Pages 프로젝트 설정: **Framework preset 없음, Build command 비움, Build output directory `prototype`**.
2. 운영 브랜치(main)는 운영 주소, `staging` 브랜치는 미리보기 주소로 나온다. 주소를 개발자에게 알려 준다.
3. GitHub "Settings → Secrets and variables → Actions"에 개발자가 알려 주는 이름으로 운영 프로젝트의 URL·공개 키를 등록한다(공개 값이지만 일관성을 위해).
4. Actions 탭에서 하루 1회 워크플로를 한 번 수동 실행해 성공(초록)을 확인한다.
5. 사이트에서 로그인·사람 수·의견 보내기를 직접 눌러 본다. 문제가 있으면 개발자가 `live:false`로 되돌린다(1분).
6. Supabase·Cloudflare 대시보드에서 **카드 등록이 없는지**, 사용량 화면 위치를 확인해 두고 주 1회 본다.
