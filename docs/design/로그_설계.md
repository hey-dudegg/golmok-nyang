# 로그 분리와 일일 백업 설계 (R-20)

마지막 반영 D-42. 설계만 있고 코드는 없다. 관련: D-01(0원), D-08, D-09, D-37, D-41, 보안_점검_설계 5장, 배포_계획 1-5(e).
전제: 상시 서버 없음. 정적 Pages + Supabase. 로그는 2차(Supabase 연결) 이후에만 의미가 있다. 1차(정적)는 브라우저 console 뿐이고 서버로 보내지 않는다.

## 1. 한 줄 결론
- 저장은 **Supabase 표**(`log_all`, `log_err`)에 쌓는다. 브라우저가 RPC 한 개로 보낸다. Workers/Functions는 쓰지 않는다.
- 일일 교체는 **`rotate_logs()` RPC**가 표 이름을 `log_all_yymmdd`로 바꾸고 새 표를 만든다. 호출은 D-09 Actions의 하루 1회 요청에 붙인다.
- 파일 `.yymmdd`는 "표 이름 접미사 yymmdd"로 대응한다. 파일 내보내기는 하지 않는다(공개 저장소에 올리지 않기 위해).

## 2. 저장 위치 비교 (0원 안)
| 후보 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Supabase 표 | 이미 쓰는 서비스, 추가 가입 없음, 500MB 안에 충분(6장), RLS로 읽기 잠금 | DB 용량 공유, 한도 초과 시 로그부터 줄여야 함 | **채택** |
| Pages Functions/Workers | 요청 시점 서버 로그, IP 처리 가능 | 현재 정적 구조에 코드·배포 경로가 새로 생김, 무료 일 10만 요청 [확인 필요: 현재 한도], 어차피 저장소는 Supabase 필요 | 보류(필요해지면 P) |
| 브라우저 오류 수집만 | 구현 쉬움 | 저장 위치가 아님(전송 대상이 필요) | 수집 수단으로만 쓰고 저장은 Supabase |
| Cloudflare·Supabase 대시보드 기본 로그 | 0 작업 | 보관 짧음·형식 우리가 못 정함 [확인 필요: 무료 보관 기간] | 보조 확인용 |

"서버 로그"의 의미: 우리 서버가 없으므로 (a) 브라우저가 보내는 사건·오류, (b) DB 함수(RPC)가 직접 남기는 사건을 서버 로그로 본다.

## 3. 로그 종류와 파트
| 표 | 내용 | 레벨 | 쓰는 쪽 |
|---|---|---|---|
| `log_all` | 중요 사건 전체(로그인 성공/실패 횟수, 글 등록·삭제, 홍보 시도·거부, 의견 접수, 일일 작업 결과, 오류 포함) | info·warn·error | 브라우저 RPC, DB 함수 |
| `log_err` | 오류·거부·경고만(`log_all`의 warn 이상을 복사) | warn·error | 같은 RPC가 두 표에 함께 기록 |

`log_err`는 파트(`part`)로 나눈다. 파트는 열 값이고, 파트마다 별도 표를 만들지는 않는다(표 수 폭증 방지, 조회는 `where part=`).
| part | 대상 | 예시 코드(`code`) |
|---|---|---|
| `server` | Supabase 연결·RPC·실시간·한도 | `rpc_fail`, `rt_over_limit`, `db_timeout`, `daily_job_fail` |
| `auth` | 로그인(D-37) | `login_fail`, `token_refresh_fail`, `provider_error` |
| `privacy` | 개인정보 관련 거부·이상 | `pii_blocked`(글에 링크·메일 형태 차단), `rls_denied`, `delete_req`(삭제 요청 접수 횟수) |
| `client` | 브라우저 오류 | `js_error`, `module_load_fail`, `webgl_fail` |
| `content` | 게시·의견·이름 | `post_reject`, `feedback_reject`, `name_reject` |
| `admin` | 어드민 행동 | `admin_action`(종류만, 대상 식별 없음) |

`privacy` 파트는 "개인정보가 새려던 사건의 기록"이지 개인정보 자체를 담지 않는다(4장).

## 4. 레코드 형식 (모든 표 동일 열)
| 열 | 형식 | 비고 |
|---|---|---|
| `id` | bigint 자동 번호 | |
| `ts` | timestamptz | 서버 시각(DB `now()`)만 쓴다. 클라이언트 시각 신뢰 안 함 |
| `lvl` | text | `info`/`warn`/`error` |
| `part` | text | 3장 목록 중 하나(아니면 `client`로 정정) |
| `code` | text | 3장 코드. 사전에 없는 코드는 `other` |
| `msg` | text 120자 이내 | 고정 문구 우선. 자유 문장·스택 전체 금지 |
| `ctx` | jsonb 300바이트 이내 | 허용 키만(아래) |
| `uh` | text 8자 | 사용자 번호의 **일별 해시 앞 8자**(아래). 비회원은 null |
| `ver` | text | 앱 버전·빌드 표시 |

- 허용 `ctx` 키: `region`(시/도 코드), `ev`(사건 이름), `n`(횟수), `ms`(걸린 시간), `status`(HTTP 숫자), `ua_class`(`mobile`/`desktop` 둘 중 하나), `file`(소스 파일 경로만, 줄 번호 포함 가능). 그 밖의 키는 RPC에서 버린다.
- `uh` = `left(encode(digest(uid || ts날짜 || 서버비밀소금, 'sha256'),'hex'), 8)`. 날마다 값이 바뀌므로 며칠에 걸쳐 한 사람을 추적할 수 없고, 같은 날 같은 사람의 오류 묶음만 확인 가능. 소금은 DB 안의 설정 한 줄(저장소·클라이언트에 없음). [확인 필요: pgcrypto `digest` 사용 가능 여부]
- **마스킹 규칙(RPC `log_write`가 서버에서 강제, 클라이언트 신뢰 안 함)**
  1. 이메일 형태(`@` 포함 토큰), `http(s)://` URL, 20자 이상 영숫자 연속(토큰 형태), `eyJ`로 시작하는 문자열, IPv4/IPv6 형태는 `msg`·`ctx` 값에서 `[x]`로 치환.
  2. 쿼리스트링(`?` 이하)과 URL 해시(`#` 이하)는 잘라낸다(OAuth 코드·토큰이 실리는 자리).
  3. 닉네임·글·댓글·의견 본문·사진 데이터는 어떤 열에도 넣지 않는다. 길이(`n`)·거부 이유 코드만.
  4. IP는 DB가 알 수 없게 둔다(클라이언트는 보내지 않고, RPC는 요청 헤더를 읽지 않는다). Supabase·Cloudflare 자체 기록은 보안_점검 5-3처럼 고지.
  5. 클라이언트는 `window.onerror` 메시지에서 위 규칙을 먼저 적용한 뒤 보낸다(이중 방어).
- 도달 못 한 로그는 버린다(재전송 없음). 로그가 서비스를 느리게 하지 않는다.

## 5. 수집 경로와 남용 방지
- 브라우저: `window.onerror`·`unhandledrejection`·`module_load_fail`·핵심 사건에서 `log_write(lvl, part, code, msg, ctx)` RPC 호출(anon 키, D-11). 모듈은 `src/adapters/`의 새 어댑터 `logger.js`(층 규칙 준수). 모의 어댑터는 console 대신 메모리 배열(모의, 비전송).
- DB 쪽: 홍보 거부(`promo_try`)·일일 작업(`daily_cleanup`)이 `log_write`를 내부에서 호출.
- 남용 방지(익명 키로 누구나 호출 가능하므로 필수): ① 클라이언트는 같은 `code` 1분에 1번, 한 탭 당 하루 최대 30건. ② RPC는 `uh` 또는 전역 기준 분당 상한(예: 전체 분당 120건) 초과 시 조용히 버림. ③ 표 직접 insert/select는 RLS로 모두 막고 RPC만 허용. ④ 읽기는 어드민 RPC(`log_read_admin`, 어드민 확인 후 `log_err`만 최근 N건)와 Supabase 대시보드 SQL로만.
- 로그 표 총량 상한: `log_all` 하루 5천 건, `log_err` 하루 2천 건 초과 시 `info`부터 버리고 `log_err`는 같은 `code`를 합쳐 `n`만 올린다.

## 6. 일일 교체·백업 절차 (배치)
수단: **D-09 GitHub Actions 하루 1회 요청**이 `rpc/daily_cleanup`을 부르고, 그 안에서 `rotate_logs()`를 호출. 별도 일정을 늘리지 않는다. 시각은 한국 자정 직후(Actions cron은 UTC, 15:05 UTC 근처. 지연 가능, 몇 분 이내 오차는 허용). pg_cron은 Supabase 무료 포함 여부 [확인 필요]이며 Actions 방식이 D-09와 일치하므로 기본은 Actions, pg_cron은 확인 후 대안.

`rotate_logs()` (SECURITY DEFINER, 멱등, 호출 권한은 anon 허용하되 동작은 "어제 이전 것만"):
1. 어제 날짜 `yymmdd` 계산(한국 시간 기준). 이미 `log_all_<yymmdd>`가 있으면 건너뜀(재실행 안전).
2. `alter table log_all rename to log_all_<yymmdd>`, `alter table log_err rename to log_err_<yymmdd>`(표 이름 바꾸기, 같은 트랜잭션에서 새 `log_all`·`log_err` 생성: 같은 열, 인덱스 `ts`·`part`, RLS 켜고 정책 없음).
3. 교체 사이 몇 밀리초에 들어온 쓰기는 잠금 대기 후 새 표로 들어간다. 실패하면 롤백되고 오늘 로그는 기존 표에 계속 쌓인다(날짜가 하루 겹침 허용).
4. 7장의 보관 초과 표를 `drop table`.
5. 결과(교체한 표 이름, 삭제한 표 수, 행 수 합)를 새 `log_all`에 info 1줄로 남김. 실패 시 `log_err`에 `server/daily_job_fail`.

Actions 쪽: 요청이 HTTP 오류면 실행을 실패로 표시(GitHub가 이메일로 알림, 추가 비용 없음). 로그 내용은 Actions 출력에 찍지 않는다(공개 저장소의 Actions 로그는 공개).

**파일 `.yymmdd` 대응**: 파일이 아니라 표 이름 `log_all_251024`, `log_err_251024`로 대응한다. 이유: ① 서버 파일 시스템이 없다 ② 파일을 저장소·Actions 산출물에 올리면 공개 위험(Actions 산출물은 공개 저장소에서 내려받을 수 있음) ③ service_role 키 없이 가능(D-11). 필요할 때 대시보드 SQL로 CSV를 내려받아 `all.251024`처럼 이름 붙여 개인 보관(저장소에는 넣지 않음)한다.

## 7. 보관·삭제
| 대상 | 보관 | 이유 |
|---|---|---|
| `log_all`(+일일 표) | 14일 | 시험 약 30일(D-41) 중 최근 흐름 확인용, DB 용량 절약 |
| `log_err`(+일일 표) | 30일 | 시험 전 기간 오류 비교. 개인정보 파트도 30일 이내 |
| 종료 시 | 시험 종료(D-41) 후 7일 내 전체 삭제 또는 이어서 운영 결정(N-2와 함께) | 보안_점검 5-2의 보관 방침과 맞춤 |
- 사용자 삭제 요청: 로그엔 `uh`(일별 해시, 소금 폐기 시 복원 불가)만 있어 개별 삭제 대신 14·30일 만료로 처리. 고지에 "오류 기록은 최대 30일, 개인을 식별하지 않음"으로 적는다(사용자 검토 후 사용).
- 로그에 닉네임·글이 없으므로 `auth.users` 삭제 cascade 대상이 아니다(보안_점검 5-2의 cascade 추가 항목과 별개).
- 개인정보 항목 대응(보안_점검 5-1·5-2): 이메일·IP·토큰·글 내용 미기록, console·토스트 금지 원칙은 `logger.js`에도 적용, reviewer가 `console.`와 `log_write` 호출처 grep.

## 8. 무료 한도 추산 (100명·30일, D-41, 모두 [추측])
가정: 하루 활동 100명 × 사람당 `log_all` 20줄(핵심 사건만, 이동·교감 등 잦은 행동은 로그 안 함), `log_err` 3줄, 한 줄 평균 250바이트(인덱스 포함 2배 가정).
| 항목 | 계산 | 결과 |
|---|---|---|
| `log_all` 하루 | 100×20×250B×2 | 약 1MB |
| `log_err` 하루 | 100×3×250B×2 | 약 0.15MB |
| 보관 최대(14일 + 30일) | 14MB + 4.5MB | 약 19MB (DB 500MB의 4%) |
| RPC 호출 | 하루 약 2,300회 | Supabase 무료 API 요청 한도 대비 매우 작음 [확인 필요: 현재 한도 수치] |
| 전송량 | 하루 약 0.6MB | 월 약 18MB (5GB의 0.4%) |
| 실시간 메시지 | 사용 안 함 | 0 |
| Actions | 하루 1회 요청(D-09 기존) | 추가 없음 |
최악(오류 폭주): 5장 상한(하루 5천+2천 건)이 막아 표 하루 최대 약 3.5MB, 30일 합 100MB 미만. 500MB의 20% 초과 시 경고(어드민 확인).

## 9. 구현 작업 단위 (2차 전, 모두 developer)
| 단위 | 내용 | 완료 조건 |
|---|---|---|
| L-1 | `log_write` 마스킹·허용 키·상한 함수와 두 표 SQL(`docs/` 또는 `supabase/`에 .sql, 값 없음) | 이메일·URL·토큰·IP 형태 입력이 `[x]`로 바뀌는 단위 시험 통과, 표 직접 select/insert 거부 |
| L-2 | `src/core/log_rules.js` 순수 규칙(마스킹·코드 사전·글자 길이) + 시험 | node 시험, 이메일·IP·쿼리스트링 사례 통과 |
| L-3 | `src/adapters/logger.js`(모의/실전 전환, 중복 제한, 전송 실패 무시) + main.js 전역 오류 연결 | 모의에선 console 미사용·메모리 기록, 오류 던져도 앱 정상, `test:imports` 통과 |
| L-4 | `rotate_logs()` + `daily_cleanup()` 연동, 재실행 안전·보관 초과 삭제 | 로컬 Postgres 또는 Supabase 시험 프로젝트에서 두 번 연속 실행해도 표 중복·행 손실 없음 |
| L-5 | `log_read_admin` + 어드민 패널 오류 목록(파트별 필터, 최근 N건) | 어드민만 열림, 일반 계정·비회원은 거부(RLS 시험) |
| L-6 | 개인정보 안내 문구에 로그 항목 추가(documenter, 사용자 검토 후) | 보관 14/30일, 식별 안 함 문구 반영 |
| L-7 | tester·security 점검: 로그 표 전체 grep으로 개인정보 샘플 부재 확인 | 가짜 이메일·토큰·닉네임을 넣고 조회해도 원문 없음 |
순서: L-2 → L-1 → L-3 → L-4 → L-5 → L-6·L-7. 2차(Supabase 연결, 로그인) 개시 전에 L-1~L-4가 끝나야 한다.

## 10. 결정 필요 사항
1. **로그 저장 위치를 Supabase 표로 확정**할지(2장). 권장: 예. (팀장 가능)
2. **일일 표를 파일로 내보낼지**: 권장 "안 함, 필요할 때 대시보드에서 개인 내려받기". 파일 내보내기에 service_role 키가 필요하면 D-11과 충돌하므로 제안만. (사용자 판단)
3. **보관 기간 14일/30일**(7장)과 시험 종료 후 삭제 시점(N-2와 합침). (사용자 판단)
4. **`uh` 일별 해시를 둘지**(없으면 같은 사용자의 오류 묶음 못 봄, 개인정보는 더 줄어듦). 권장: 둠. (팀장 가능)
5. pg_cron 무료 포함 여부, pgcrypto 사용 가능 여부, Supabase·Cloudflare 무료 한도 현재 수치: **확인하지 못함**, L-1·L-4 착수 전 사용자 또는 security가 대시보드에서 확인.
6. 1차(정적 공개) 단계에서는 서버 로그가 없으므로, 오류 파악용 최소안(사용자 제보는 의견 보내기)으로 충분한지. (팀장 가능)

## 11. 확인하지 못한 것
- Supabase 무료 플랜의 API 요청·로그 보관 정책, pg_cron·pgcrypto 사용 가능 여부(2025~2026 기준 변경 가능).
- Actions 일정 시각이 정확히 지켜지는지(지연 가능, 설계는 멱등으로 대비).
- 일별 해시 `uh`가 법적으로 개인정보에서 제외되는지(법적 판단 아님, 안내 문구는 보수적으로).
